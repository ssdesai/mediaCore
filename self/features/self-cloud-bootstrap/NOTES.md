# Notes: self-cloud-bootstrap

Rulings made during the direct build, one line of rationale each. Round 1 (`2ed6b67`)
built the brief's design — a tracked bootstrap `.claude/settings.json` whose one
`SessionStart` hook ran `wire-settings.py --self --write`, the full policy in the untracked
`.claude/settings.local.json`. Live evidence ("The open question (live)" below) replaced
it: round 2 TRACKS the whole policy in `.claude/settings.json`, its `PreToolUse` command
guarded to a no-op where `${CLAUDE_PROJECT_DIR}/hooks/allow-repo-commands.sh` is absent,
and generates nothing else. These are the calls each round left open.

## Rulings

### Round 1, as they stand now

- **The bootstrap command is the brief's** — superseded: there is no bootstrap.
- **`--write` rewrites only the file(s) that differ** — superseded: one file.
- **`--check` names every differing file, the policy first** — superseded: one file.
- **Vendored `--check` does NOT compare the bootstrap** — superseded: a vendored
  `--check` compares the shipped policy byte for byte (round 2, below).
- **The vendored rule keys on the policy file only** — superseded: no rule about
  `settings.local.json` remains; the vendored check is the byte comparison.
- **Both files come from one function each (`bootstrap_text()`, `self_files()`)** —
  superseded: both functions are gone; `generated_text(True)` is the one file.
- **The gate section is renamed to name both files** — superseded: it is
  `permission policy wired into .claude/settings.json` again.
- **Bootstrap command assertions live in `self-settings.sh` section F** — superseded in
  content, kept in place: F now runs the guarded hook command.
- **"Nothing written" is `git status --porcelain --ignored --untracked-files=all`
  unchanged** — stands; round 2 uses it in A, C and F and feature-lifecycle S1v.
- **`feature-start.sh --self` keeps "only when missing"** — superseded: the block is gone.
- **`self/worktree-setup.sh` still writes the policy** — superseded: it writes nothing.
- **The test fixtures commit the generator's bootstrap** — superseded: they commit the

### Round 2

- **The guard is a named pair of constants**: `SELF_HOOK_PATH` and
  `SELF_HOOK_COMMAND = 'test ! -f "<path>" || "<path>"'`, so the generated command is the
  brief's string exactly and the unguarded path stays nameable (hook-wiring.sh uses it as
  the drift case that replaced "repointed at the vendored path").
- **The payload does reach the hook through the guard**: `test` reads no stdin, so the
  second command inherits the whole payload; self-settings.sh Fb/Fc prove it by getting
  the hook's `deny` back through `sh -c`. A hook file without its executable bit would be
  a non-blocking hook error; it is tracked `100755`, and nothing changes that.
- **Vendored `--check` compares the shipped bytes**: the file ships with the subtree and
  is generated by the same code, so an equal file is `in-sync` ("the subtree's copy"), a
  drifted one `UNWIRED`, a missing one `missing`. A failure names the fix **upstream**
  (`VENDORED_FIX_HINT`: regenerate in a standalone checkout, commit, pull) and no
  `--repo <vendored dir>` command, since a vendored `--write` writes nothing. Chosen over
  "always pass" because a consuming repo whose vendored copy was hand-edited, or a
  vendored build that changed the constants, would otherwise ship a policy nobody checks.
- **Vendored `--write` reports the same status `--check` would, plus "nothing written"**,
  exiting 1 on a mismatch: a write that cannot do its job says so rather than `kept`.
- **The residual vendored limit is a backlog entry**: a vendored `--self` build that
  changes the policy goes red with no local fix. Round 1's vendored-bootstrap entry is
  rewritten to that shape rather than dropped, since the limit is real work if wanted.
- **Standalone messages ask for a commit**: `--write` says "it is tracked — commit it",
  and the regenerate hint is "regenerate it: <command>, then commit it" — the
  regenerate-command regex the tests use still matches it.
- **`feature-start.sh --self`'s regenerate-when-missing block is removed with its two
  constants**, and the backlog entry "regenerating the primary's settings 'only when
  missing' is untested" with it: there is no regeneration left to test, and a primary
  receives the file with the fast-forward (ruling 3 of "The open question (live)" below:
  git overwrites an ignored copy).
- **`self/worktree-setup.sh` keeps `template-version: 2`**: its only job is now sourcing
  `self/environment.sh`, the same contract as the template's; `sync-check.sh` 8 compares
  the numbers and is green, and `self/` scripts are not in the template hash table.
- **The "don't ask again" backlog entry is removed**: `.claude/settings.local.json` is
  ignored and never generated or compared, so a grant written there touches nothing.
- **F's payload is the brief's, with no `session_id`**: the hook keeps an escalation
  counter only for a payload that names a session (`state_path()` returns None
  otherwise), so this payload writes nothing anywhere and is denied every time. `TMPDIR`
  is a scratch directory asserted empty afterwards (F4), so a regression that started
  writing state would show.
- **F's "nothing written" in the consumer** uses the same `tree_state`, and the E
  section's edits to the consumer's root file are reverted before F so it starts clean.
- **feature-lifecycle S1v is reshaped, not dropped**: the start writes nothing under the
  primary's `.claude/` (ignored files included), prints no `settings` line, and the
  tracked file is the generator's in primary and worktree; S6i adds that the vendored
  copy the consumer ships is left as shipped.
- **cloud-start's fixture drops `.claude/` entirely**: a `--self` start no longer needs a
  file present to avoid a regenerate warning.
- **hook-wiring regains main's "`--self` on a vendored file reports UNWIRED"** case, which
  round 1 had replaced with a two-file variant.
- **The feature's own `README.md` prose is updated** to the round-2 design; its fence is
  untouched.
- **This checkout's stale round-1 `.claude/settings.local.json` is left on disk** (ignored;
  the brief forbids writing under `.claude/` by other means). Claude Code merges it over
  the tracked file, which would run the hook twice (once unguarded) in a session launched
  here; named in the report for the coordinator to remove.
- **Merge of `origin/main` (#83 session-start-precision)**: #83's `record_fresh` mode in
  `self/gate.sh` is kept and the settings check stays on it — its reason (the file is
  ignored, so the tree sha cannot see it) is gone, but a fresh check is cheap and always
  describes the working copy a session loads; the comments and READMEs now say so.
  #83's `self-settings.sh` section F (resumed gate still fails a deleted or drifted file,
  no gate-state record) becomes section **G** (G1–G4) after ours (0, A–F), run through a
  `run_gate_resumed` helper that sets `GATE_RESUME=1` per run while the top-level
  `unset GATE_RESUME` stays; its D1–D2 ("not tracked", "ignored") are dropped for ours.
  G4 is now the assertion that pins `record_fresh`, since a tracked file's deletion moves
  the sha anyway. #83's millisecond changes are untouched.

## The open question (live) — ruled 2026-10-05 by the coordinator

Does a hook or deny rule written into `.claude/settings.local.json` by a `SessionStart`
hook take effect in that same session, and does a consuming repo ever load a vendored
`agentTooling/.claude/settings*.json`? Claude Code 2.1.289 (headless `claude -p`, this
container) and 2.1.290 (the cloud sessions). The docs (settings.md) say settings files are
watched and edits to `permissions` and `hooks` reload into the running session; they are
silent on a file written during startup and on a nested project's settings.

**Ruling 1: a SessionStart-written policy takes effect in the same session, but NOT
reliably before its first tool call — a race. So the proposed bootstrap design (round 1,
commit `2ed6b67`) is replaced: the hook and the deny rules live in the tracked file
itself.** Evidence, each a fresh clone of `2ed6b67` whose bootstrap wrote the local file
during startup (`hook_response` "created .claude/settings.local.json" before `init` every
time), the first tool call `python3 -c 'print(1)'`:

| Launch | Fresh sessions | `PreToolUse:Bash` fired on the first call |
|---|---|---|
| `--allowedTools Bash`, one-step prompt (probe 2, probe 3) | 6 | 6 |
| `--permission-mode acceptEdits`, one-step prompt (probe 4) | 3 | 3 |
| `--permission-mode acceptEdits`, two-step prompt (probe 1, probe 5) | 6 | **3 — probe 1 itself and two of its five repeats missed: no `PreToolUse` event at all, the call went to the ordinary permission flow** |
| a cloud session, `create_session` on the branch (acceptance below) | 1 | 1 |

Three misses in fifteen headless fresh sessions, none in any session whose file existed at
startup (probe 2's and probe 4's second sessions, 4 of 4). The file watcher reloads
asynchronously after the SessionStart hook returns, and a quick first tool call can beat
it. A miss is not an approval — the command reaches the ordinary permission flow — but for
that call neither the hook nor any deny rule exists, which is the exact gap the backlog
entry describes. A tracked file is read at startup, before any tool call, with no race.

**Ruling 2: a consuming repo loads the vendored file only when a session is launched INSIDE
`agentTooling/`, and there every path it names exists — so tracking the full policy ships
nothing harmful.** Evidence (probe 1, a consumer repo with `agentTooling/` vendored, no
`.git` of its own, root wiring by `sync-plans.sh`'s merge):

- launched at the consumer root: one SessionStart event, the root's own
  (`plans/cloud-setup.sh`); the vendored bootstrap's never ran. The root's `PreToolUse`
  hook denied `python3 -c`. Nested settings are not loaded.
- launched in `consumer/agentTooling/`: the VENDORED bootstrap ran (it printed `in-sync …
  absent, as a vendored copy's must be`), and the consumer root's hook did NOT fire — the
  project is the launch directory, not the git root. `${CLAUDE_PROJECT_DIR}` is then
  `…/agentTooling`, so `${CLAUDE_PROJECT_DIR}/hooks/allow-repo-commands.sh` exists. The
  `self-settings-untracked` premise — "naming a hook path that does not exist there" — does
  not hold for any session that loads the file; such a session (a `--self` executor's cwd
  is this directory, `CLAUDE.md`) is better off WITH the self policy than with none.

**Ruling 3: a fast-forward over the commit that tracks the file needs no migration.** Git
overwrites an ignored untracked file when a fast-forward starts tracking that path, with
identical or different bytes (scratch probe, both cases `ff OK`), so a local primary
holding the old generated file just takes the tracked one.
