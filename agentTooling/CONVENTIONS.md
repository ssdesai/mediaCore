# Conventions

Shared working conventions for Claude Code, vendored into each repo and imported
by its root `CLAUDE.md`. Everything here is repo-agnostic. Project-specific facts
— real field lists, real file paths, build and test commands — belong in the
consuming repo's root `CLAUDE.md` below the import, not in this file. Nothing about
plan authoring, branch naming or the feature lifecycle belongs there either: this file
and `AGENT_PLANS.md` carry those for every repo, and the lifecycle scripts refuse a bad
branch name themselves.

Plans are authored per `AGENT_PLANS.md`, which overrides parts of this file during plan
generation. Before authoring one, read the repo's `plans/PROJECT_FACTS.md`
(`self/PROJECT_FACTS.md` for agentTooling's own features): the facts a plan must pin so a
cold-start executor does not re-derive them.

## File Access

- Do not read files or folders listed in `.gitignore` (e.g. `node_modules/`, `venv/`, `.env`, `__pycache__/`, build artifacts, etc.)
- Do not read files or folders that contain only autogenerated metadata (e.g. `.DS_Store`, `*.pyc`, `*.egg-info/`, `.mypy_cache/`, `.ruff_cache/`, `dist/`, `build/`, lock files like `package-lock.json` or `uv.lock` unless directly relevant to a dependency issue)

## Shell commands

Every Bash call meets one of three outcomes, decided by what the policy could learn from
reading it rather than by what the command does: **approved silently** (read-only and
confined to the project root), **sent back with a rewrite** (a shape nothing can read,
denied with the rewrite as the reason), or **handed to the human** (a write, an unknown
program, a path outside the root). One rule produces every row below: **every path a
literal, every program named, nothing decided at run time.** Where
`hooks/allow-repo-commands.sh` is wired the rows are enforced and each denial names its
fix; `hooks/README.md` has the reasoning behind each shape.

**Approved silently.** Reads and tests, confined to the project root: `ls`, `cat`,
`head`, `tail`, `wc`, `grep`, `rg`, `find`, `sed -n …p`, `stat`, `du`, a read-only `git`
(`status`, `log`, `diff`, `show`, `branch --show-current`, `worktree list`, `stash list`,
behind `-C <path inside the root>` as well), the test and lint runners (pytest, ruff,
mypy, `npx playwright test`, the named `npm run` scripts), and the harness's own
read-only entry points (`gate.sh`, `check-plans.sh`, `bash -n`, `shellcheck`,
`py_compile`, `report.py`, a listing `capture_planning.py`, `manifest.py get`). A
standalone `cd <absolute path>` inside the root is approved, and the directory persists
into the next call.

**Sent back with a rewrite.** Rewrite it as the reason says rather than retrying it;
`pushd` and a subshell are denied too.

| Shape | Example | The rewrite |
|---|---|---|
| a `cd` or `pushd` chained with another command | `cd src && ls` | `cd <absolute path>` as its own call, then the command |
| an assignment whose own `$NAME` is used later on the line | `X=/p; cat $X/f` | inline the literal — you still have it, two words earlier |
| a `$NAME` or `${NAME}` the shell will expand, anywhere in a word — the special and positional parameters (`$?`, `$$`, `$1`) included | `grep x $FILE`, `ls "$HOME/f"`, `cat $1` | inline the literal |
| a `~` | `ls ~/x` | write the absolute path |
| a `..` component in a path | `cat ../x`, `ls a/../b` | write the path from the project root |
| a bare or relative `cd` | `cd src`, `cd` | `cd <absolute path>` |
| a line break outside a quote or a heredoc, or a `\` continuation | two commands on two lines | one call per line |
| a brace group the expansion refuses (a quote or backslash mixed into an unquoted brace group, nesting, past the cap) | `cat {a,{b,c}}` | expand it yourself, or write a script |
| a heredoc feeding anything but `cat` | `python3 - <<'EOF'`, `bash <<EOF` | write the script to the scratchpad and run it by name |
| code handed to an interpreter as a string, including behind `xargs` and `find -exec` | `python3 -c`, `bash -c`, `node -e`, `perl -ne`, `eval` | the same |
| a pipe into an interpreter with no script file, redirect or not | `… \| sh`, `… \| python3 > out` | the same |
| a program decided at run time | `$CMD …`, `$(which x) …` | the same |
| a `$(…)` or backtick inside a word that is a path | `ls $(cd dir && pwd)/src` | inline the literal |
| a one-line `for`, `while`, `until`, `if` or `case` | | write the script and run it by name |
| a line that does not tokenize | `cat 'x` | close the quote |
| a sequence mixing approved reads with one command the human must judge | `grep x f && git commit -m m` | run the reads on their own — they are approved — and the other alone |
| a `sleep`, anywhere on the line | `sleep 60`, `ls && sleep 5` | nobody polls: run the long command in the background and wait for the notification it sends when it exits (`ORCHESTRATION.md`) |
| a file authored through the shell: `echo`/`printf` redirected to a path, `cat`/`tee` fed a heredoc, a herestring or an `echo` with output to a path, `sed -i` | `cat >> f <<'EOF'`, `echo x > f`, `sed -i 's/a/b/' f` | the Write tool for a new file or a whole rewrite, the Edit tool for a change — an append is an Edit on the file's last lines |

Exempt: a heredoc feeding `cat` is a literal string, not code (`git commit -m "$(cat
<<'EOF' … EOF)"` is the shape Claude Code itself uses), as is a `$(…)` that is a whole
argument rather than part of a path. After two such denials in one session the policy
stops correcting and asks the human instead; under a batch runner it prints nothing then,
and the executor has a scratch directory of its own (`RUNNER.md` → "The executor's
environment").

**Handed to the human.** One write per Bash call, and nothing else on the line: reads go
in their own calls, where they are approved with no prompt, so the one thing the human
agrees to is the thing they were shown. `cd <absolute path>` as its own call rather than
`git -C <another tree> …`. What reaches them is a write with no tool to do it instead — a
captured output (`pytest > out.log`), a copy, a move. A file whose content you wrote in
the command is not theirs to approve: author files with the Write and Edit tools, never
through the shell, wherever the file is. A subprocess write is checked against neither
the repo's `Edit` allow rules nor its deny rules, so it is sent back. Write each file
once: compose the final content, then write it.

## Closing a feature

After a feature's review comes back `Verdict: clean`, run `feature-close.sh` (with
`--self` for an agentTooling self feature) straight away, without asking first. The PR it
opens is the expected outcome of a clean round, and the repository owner has authorized it
as a standing rule (`LIFECYCLE.md` → step 5). An escalated verdict is a new round, never a
close.

## READMEs

Each folder has a `README.md` describing its contents. It is the folder's index: what
each file is for, and the two kinds of fact a file listing cannot show (Rules 1 and 2
below).

### Generated READMEs

A README whose header says it is generated — written by a sync and overwritten on every
pull, as a consuming repo's `plans/README.md` is from `agentTooling/templates/` — is
**never edited**, not even to list a file you just added to its folder: the next sync
drops the edit. Its folder's repo-specific contents, exceptions and elaborations go in the
repo-owned file its header names (for `plans/`, `PROJECT_FACTS.md`), and that file is the
one the rules below have you keep current. Nor is the template edited to carry a
repo-specific entry: it ships to every repo that vendors it.

### Navigating the codebase

- In a repo you do not know, start from the root `README.md`.
- Before editing in a folder, read its `README.md`: it names the contracts the files
  there depend on and what the folder's tests cover. A long README is read by section —
  the entry for the file you are changing — not whole.
- Search (Grep, Glob) is the right tool for locating a symbol or a usage; a README is the
  right tool for learning what a thing is for and what depends on it. A grep hit in a
  file whose README entry you have not read is a file whose contracts you have not read.

### Keeping READMEs up to date

Before considering a change done, for every folder it touched (files added, removed or
significantly modified): read that folder's `README.md`, verify it still describes the
folder — field lists, file descriptions, cross-references — and update it where it does
not; a generated README is updated through the repo-owned file it names ("Generated
READMEs" above). Check the parent folder's README too when the change affects what it
says about the subfolder. A new file, a renamed field or a changed signature is enough to
make a README misleading.

### Required README content

The two rules below apply **only when an entry matches the trigger condition**. Entries that don't match (pure utilities, constants files, CSS, scripts, fixtures, ordinary React component descriptions, etc.) follow the regular README guidance and need no extra treatment.

**Scope discipline:** Apply these rules to entries you are creating or modifying as part of your current task. Do not proactively audit and rewrite unrelated entries that happen to violate the shape — that's its own task, only do it if explicitly asked.

**Rule 1 — Field lists for cross-module data shapes.**
Trigger: the entry describes a *data shape that is serialized, persisted, or returned across module boundaries* — e.g. Pydantic schemas (especially `*Out` / response types), TypeScript types/interfaces exported and consumed by other files, hook return objects used by multiple components, on-disk JSON formats. Does **not** apply to React component prop interfaces, internal-only types, or local helper return types.

Shape: list every field, not just summarize purpose.
> - `order.py` — `OrderOut { id, customer_id, status, total, line_items }` — returned by order CRUD endpoints.

The field list is what makes omissions visible on a read. A summary like "used for node CRUD" hides bugs.

**Rule 2 — Naming non-obvious cross-layer dependencies.**
Trigger: the entry describes a module whose correctness depends on a contract that is *not visible from its imports* — e.g. an API response field assumed to be present, an env var, a magic file path or filename, a field on a prop that originates several layers up, a sibling module's runtime behavior. Does **not** apply to ordinary imports (the import statement itself is the visible contract).

Shape: name the dependency so a reader can see the contract without running the code.
> - `OrderSummary.tsx` — … Requires `order.customer_id` on the Order prop; depends on `OrderOut` including `customer_id`.

If the module is self-contained or its dependencies are all visible at the import line, this rule doesn't apply.

## Debugging

When a runtime error carries a literal `undefined`, `null` or `[object Object]` in a URL
or payload, the bug is a serialization or typing gap: start at the response schema or
type definition that produces the value, not the UI that renders it — the field lists
README Rule 1 requires are what name that schema. Form a hypothesis and test it at the
suspected source before widening scope; for a UI bug that reading has not found, run the
app and observe the behaviour.

## Code style

### Named constants

All magic values — colors, sizes, weights, opacities, zoom levels, timeouts, URLs, or any other literal that carries meaning — must be assigned to a named constant at the top of the file before use. Inline literals in render/logic code are not acceptable.

**Rules:**
- Group related constants with a short label comment (e.g. `// Node path style`, `// Map initial view`).
- Name constants to explain intent, not just value: `NODE_DIMMED_OPACITY` not `OPACITY_025`.
- When a value has a per-type lookup (e.g. radius by asset type) AND a fallback for unknown types, declare both as separate constants: the lookup record and the fallback scalar.
- The same constant must be reused wherever the same value is needed — never duplicate a literal even if it appears in a different context.

**Example structure for a component with visual config:**
```ts
// Node appearance
const NODE_FILL_OPACITY = 0.9;
const NODE_DIMMED_OPACITY = 0.25;
const NODE_RADIUS_BY_TYPE: Record<string, number> = { person: 7, institution: 10 };
const NODE_RADIUS_FALLBACK = 8;
```
