# `Track.artist`: the track-level artist the release bundle was dropping

vinylCatalogue's `plans/BACKLOG.md` (raised by `compilation-artists-and-runout`'s review):
its export adapter projects each `record.json` track into `mediacore.Track`, whose fields
are `{ position, title, duration, credits }` — there is no `artist`, so a signed-off
compilation exports with no track artists at all, at the only point the data leaves the
system (its spec §7.10, `INTEGRATION.md` §5.1). That fix "needs an `artist` field on
`mediacore`'s `Track` first". This feature is that field, built as one direct one-shot
(`../../../agentTooling/AGENT_DIRECT.md`). The adapter change is vinylCatalogue's
`bundle-track-artist`, after this is merged and tagged.

## The decision

1. **The field.** `Track` in `src/mediacore/release.py` gains `artist: str | None = None`,
   after `title`. Meaning, in its docstring: the artist credited against this track as
   the release prints it — compilations, splits, various-artists releases. `None` means
   the release prints no track-level artist; it does **not** mean "same as the release
   artist" (absence is absence — a consumer that wants a display artist falls back
   itself). `Credit` is untouched; a track artist is not a role credit.
2. **Versioning, from `INTEGRATION.md` §12 applied to what `ContractModel` does.**
   `ContractModel` forbids extras, so a `mediacore` 0.2.0 reader rejects any bundle that
   carries `artist`. That makes this an on-disk `release.json` shape change, not a purely
   additive one: `SCHEMA_VERSION` goes `1` → `2`, the package version goes `0.2.0` →
   `0.3.0`, and the tag to cut after merge is `v0.3.0`. A 0.3.0 reader still reads a
   schema-1 bundle (the field defaults). Consumers re-pin deliberately, per §12 — that is
   their work, not this feature's. The tag is created by the human after the PR merges,
   never by this feature.
3. **The docs.** `INTEGRATION.md`: the `Track { … }` shape line; the mapping paragraph
   that says `tracks` come from `record.tracklist` gains `artist` from
   `record.tracklist[].artist`; §12's versioning paragraph gains the 0.3.0 line in the
   style of the 0.2.0 one; §13's decisions log gets an entry dated 2026-09-06 with the
   reasoning in point 2; the musicMap/humanNetworkMap consumer notes say the field may
   be ignored by an importer that has no use for it. `README.md`, `plans/PROJECT_FACTS.md`
   → Types, and the `src/mediacore/` README field list all say the new shape.
4. **The fixture.** `fixtures/its-saxy/release.json` is regenerated by
   `scripts/make_fixture_its_saxy.py` (the gate re-runs it and fails on a diff, so the
   regenerated file is committed). Its `schema_version` becomes 2. Whether a track with
   no artist serialises the key as `null` or omits it follows whatever `write_bundle`
   already does for the other optional fields — do not special-case it; record which in
   NOTES.
5. **Tests**, in `tests/test_release.py` and `tests/test_bundle.py` per the tests README:
   a `Track` with `artist` round-trips through a written and re-read bundle; one without
   reads as `None`; a schema-1 bundle — the previous checked-in `release.json`, frozen
   under `tests/` as a test asset — still reads; a bundle whose `schema_version` is 3 is
   still refused. `tests/test_fixture.py` stays green against the regenerated fixture.

## Deliberately excluded

- Every consumer's re-pin: vinylCatalogue's adapter (`bundle-track-artist`, next),
  humanNetworkMap's and musicMap's importers (they re-pin when they next need to read a
  new export; until then a 0.3.0-exported bundle is refused by their 0.2.0 readers with
  the schema-version message, which is the designed behaviour).
- Any per-track `refs` for the artist (a `discogs:artist` ref on the track itself). The
  backlog asked for the artist; refs on tracks are a separate §3 question.
- Creating the tag.
